# SolokPDF を閲覧者の操作から見直す（E158）

2026-11-28、Windows 版 `solokpdf-dev` の `91f27f5d9` を対象としたレビュー。今回の成果物は診断と修正計画。E157 で完了した変更を含む現行コードを基準とする。[前回の判定](design-review-plan.md) · [作業台帳](backlog.md)

## 製品としての判断

**PDF を開いて読む道筋は短い。** ファイルを開く、ページに合わせる、幅に合わせる操作は各メニューの直下にある。本文の右クリックでは、文字を選ぶと「コピー」、リンク上ではリンク先のコピーを先頭に出す。PDF の結合・署名などは「ツール → PDF 操作」に置いている。私ならこの配置を保つ。読みにくさが現れるのは機能数そのものより、検索中に何が起きているか、保存ボタンがどのファイルの上書きを意味するかを読み取れない場面である。[メニューの操作試験](../../tests/solok-menu-layout.ts)

**二つの PDF エンジンを持つ理由はある。** PDFium の本文表示を選んだ製品で、開けない PDF のフォールバック、ページ単位の代替描画、編集用 MuPDF の遅延生成は別々の判断である。パスワード入力を中止したときは再試行を止め、墨消し適用後は編集済みページを描く。日常操作からエンジン選択を隠せている。保守上の代償は、同じ文書でも「いま何を読んでいるか」を用途ごとに追う必要があること。今回の保存失敗は画素を取り出した**後**で起きた。まず両エンジンが通るファイル出力を直すのが効果的である。[生成とフォールバック](../../src/shared/EngineCreate.cpp) · [ページ描画と編集](../../src/solokpdf/EnginePdfium.cpp) · [現行設計](architecture.md)

**安定性の判定。** 現行 Debug を非表示デスクトップで実行。PDFium で小さな PDF 2本を開き、ズーム・スクロール・検索・タブ切替・全タブを閉じる操作を2分間で314周完走した。10秒ごとの12標本で GDI オブジェクトは262のまま、ハンドルは517から514となり、Private Bytes も試験の増加判定を通った。通常の短時間閲覧には肯定的な結果である。大きな実文書の長時間利用や終了時の資源解放までは、この試験から判定できない。保存には以下の再現性のある例外がある。[反復試験の操作と判定式](../../tests/ad-hoc-pdfium-leak.ts)

**UI の判定。** 英語表示・820 × 640 の実画面では、PDF 本文の上にタブとツールバーが1段ずつあり、閲覧中に操作説明が本文を占めることはなかった。750 px 幅のメニュー試験でもリンク先コピー、画像保存、倍率変更、Home からの「開く」が通った。一方、Home で履歴の検索結果が0件になった画面では、広い空白の下に設定変更ショートカットのヒントだけが残った。本文に説明を増やすより、このように利用者が次の判断を必要とする状態に表示を絞りたい。今回の直接観察は英語 Debug。日本語表示、読み上げ音声、初見の利用者による操作性は未評価。[メニュー試験](../../tests/solok-menu-layout.ts)

### 問題が生じる階層

| 層                     | 現れる問題                                                                                 | 修正する境界                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 利用者に見える操作     | 「変換」しただけで既存画像が消える。履歴の空欄や licenses の表示から次の操作が読み取れない | ボタンの約束、検索結果、リンクの意味を実際の処理に合わせる（1B・2C・3A）   |
| ウィンドウと文書の状態 | 別窓のページ番号を表示できてしまう。画面で選べる履歴を UIA では選べない                    | 検索中の窓と、表示中の履歴項目を状態の所有者にする（2A・2B）               |
| ファイルの生成と公開   | 成功・失敗にかかわらず、処理途中から最終ファイル名を書き込み・削除に使う                   | 一時ファイルの所有者と、最終名の置換可否を明示する（1A・1B）               |
| 検証                   | 件数、ラベル、正常終了だけを見ると、元のデータや選択対象の取り違えを見逃す                 | 元バイト、2窓の進捗、外部 UIA クライアント、表示ラベルと実リンクを照合する |

## 1. 保存とデータ保全

### 1A　高・再現　画像を書けなかったとき、元のファイルまで消える

**操作と結果。** 2ページ PDF を PDFium で開き、既存の出力先を読み取り用ハンドルで保持した。共有モードは読み取りと削除を許可し、書き込みを拒否。矩形選択を PNG に保存すると `ERROR save-failed`、1ページを BMP に変換すると `ERROR convert-failed`。ハンドルを閉じると、どちらの出力先からも元のファイルが消えていた。Debug の制御 API から、各ダイアログと共通の保存処理を実行した。

**根本。** `WriteSelectionPixmap` は最終パスに直接 PNG を書き、失敗するとそのパスを削除する。ページ画像と PNG 以外の選択画像が通る `SavePixmapAsImageFile` も、エンコーダー失敗時に最終パスを削除する。「今回作った未完成ファイル」を指す名前を所有していないため、失敗前から存在したファイルまで後始末の対象になる。既存の部分失敗テストは、出力と同名の**ディレクトリ**を作っており、この条件を通らない。[選択・ページ画像の出力](../../src/shared/PdfToolsCommon.cpp) · [Win32 エンコーダー](../../src/PdfTools.cpp) · [既存テスト](../../tests/convert-images-partial.ts)

**Sol の作業。** 画像1枚を公開の単位にする。親ディレクトリを作り、同じディレクトリの一時ファイルを所有し、エンコードとフラッシュの成功後に公開する。既存の `PdfToolOutput` の寿命管理と `Publish` を再利用できる。エンコーダーを最終名の拡張子で選ぶか一時名に適切な拡張子を与える。PNG の再圧縮は公開成功後に始める。[既存の出力境界](../../src/shared/PdfToolsCommon.cpp) · [置換処理](../../src/base/File.cpp)

**合格条件。** 意図した上書きの成功時は新画像を開いて画素と寸法を照合する。置換を拒むハンドルで公開を失敗させた場合は、元ファイルがバイト一致し、一時ファイルが残らないこと。上記の「削除だけ共有できる」条件は修正後に正常な置換が可能なので、成功なら完成画像、失敗なら元バイトを要求する。複数ページの一部失敗では成功ページを残し、失敗ページ番号を表示する。[範囲 PNG・JPEG](../../tests/issue-6127.ts) · [部分失敗とキャンセル](../../tests/convert-images-partial.ts)

### 1B　高・再現　「変換」の表示後にできた同名ファイルが上書きされる

**操作と結果。** 2ページ PDF の画像変換ダイアログで保存先を空のフォルダーの `page-<N>.png` に指定した。「変換」の表示後に別プロセスから `page-2.png` に目印を書き、ダイアログの「変換」を押した。警告は出ず、目印が PNG に置き換わった。

**根本。** `UpdateExisting` は入力変更時のファイル数を調べて「変換／上書き」を表示する。`DoIt` がワーカーへ渡すのは出力先テンプレートとページなどで、利用者に提示した上書き対象を渡さない。`ConvertPagesToImages` は各ページを最終名に保存する。1A の一時ファイル化だけでは、後からできたファイルに完成画像を上書きする問題が残る。[ダイアログとワーカー](../../src/PdfTools.cpp) · [名前生成と保存ループ](../../src/shared/PdfToolsCommon.cpp)

**Sol の作業。** 1A の公開処理に「新規作成」と「表示済みの対象を置換」の区別を持たせる。新規名は最終公開時にも置換を許さず、衝突したページを既存の部分失敗通知に含める。「上書き」は画面で数えた対象に限る。全ページの事前再チェックだけでは、確認と公開の間の競合が残る。総数や現在ページを変更したら確認対象も更新する。

**合格条件。** 空の出力先で2ページを選び、「変換」が見えてから2ページ目の予定名に目印を書き、実際のボタンを押す。1枚目は読め、目印は元の内容のまま、失敗は2枚目と分かる。最初から存在して「上書き」を選んだ画像では置換が成功し、「新しい名前を使用」では旧ファイルが残る。既存試験は候補名とボタンを調べて閉じるため、この実行ケースを加える。[名前衝突の試験](../../tests/issue-6439.ts)

## 2. 日常の操作と状態の所有者

### 2A　中・コードで確認　別ウィンドウの検索が進捗ページを共有する

**現象と根本。** A の検索がページ2、B がページ80を通知し、次に A の部分結果が「件数だけ」を届けると、A は自分の文書で80のページラベルを引く。PDFium では範囲外のページにも数値文字列が返るため、存在しないページ番号も表示し得る。検索スレッドと世代番号は窓ごとだが、`SetFindCountProgressStatus` が最後に見たページだけはプロセス全体の `gFindCountCurPage` にある。最終ヒット一覧への混入は確認していない。[進捗・部分結果の処理](../../src/shared/SearchAndDDECommon.cpp) · [ページラベル](../../src/solokpdf/EnginePdfium.cpp)

**Sol の作業と合格条件。** 部分結果にその検索のページを含めるか、最後のページを窓の検索状態に置いて検索開始時に初期化する。既存の世代確認を通してから表示する。ページラベルの異なる2窓で上記の通知順を固定し、A の部分結果後も A のページを表示すること。B の進捗・最終件数、旧検索を取り消して次の語を検索した結果も照合する。表示文言の変更は不要。[2窓の検索 UI 試験](../../tests/find-ui-state.ts) · [タブ切替の試験](../../tests/ad-hoc-find-tab-switch.ts)

### 2B　中・再現　Home の最近使ったファイルを UI Automation から選べない

**操作と結果。** 履歴を1件表示した Home で、外部の Windows UI Automation クライアントからキャンバス配下を列挙した。得られたのは名前のない Pane と Custom の「Start Page」。画面にある PDF の名前を持つ項目は0件だった。

**現象と根本。** マウスや矢印キーで移動できる履歴項目を、Home の UI Automation（UIA）プロバイダーから列挙できない。`WM_GETOBJECT` はキャンバスのルートを返すが、その子 `StartPageProvider` は子要素も操作パターンも返さず、フォーカス照会もルート側で Start Page に止まる。独自描画で持っている「どのファイルか」「何を選んだか」が読み上げ側に届かない。文書本文の読み上げ、ネイティブ検索欄、サイドバーの木は別経路である。[Home のプロバイダー](../../src/uia/StartPageProvider.cpp) · [親とフォーカス](../../src/uia/Provider.cpp) · [キーボード操作](../../src/CanvasAboutUI.cpp)

**Sol の作業と合格条件。** 履歴一覧・項目名・選択・開く操作を、画面と同じ絞り込み結果に結び付ける。既存の「開く」導線も実際の UIA ツリーで点検する。同名・別フォルダーの2項目を区別でき、リスト／サムネイルで同じ項目を選択・起動できること。検索欄のフォーカスを奪わず、フィルター変更や別文書への切替、窓を閉じた後に古い項目を呼んでも別ファイルを開かないこと。外部 UIA クライアントで確認し、失効した参照のケースを ASan でも通す。本文用クライアントは `ShowStartPage = false` なので Home のケースを分ける。[UIA 試験](../../tests/ad-hoc-uia.ts) · [既存のツリー実装](../../src/TreeUia.cpp)

### 2C　低・設計提案　Home で検索が空振りしても、残る説明は一般的なヒント

**現象と根本。** 履歴がある状態で一致しない名前を入れると一覧が空になる。レイアウトは一致数に関係なく有効なヒントの高さを確保する。ファイルを見つけられなかったことより、今回の操作と無関係な機能の説明が目につく。さらに、絞り込みは `LayoutHomePage` と `CollectHomePageFiles` に重複し、`CountHomePageFiles` は件数のために並べ替え済み一覧を再取得する。一致件数を別計算で増設すると表示と選択がずれやすくなる。[Home の表示](../../src/HomePage.cpp) · [履歴の収集](../../src/shared/HomePageCommon.cpp) · [並べ替え](../../src/shared/FileHistory.cpp)

**私ならこうする。** 非空の検索語で一致がゼロのときだけ、一覧に短く「一致するファイルはありません」と出し、その間は一般ヒントを隠す。「開く」と既存の Esc で戻れる。履歴がもともと空の初回画面には検索失敗を出さない。検索キーの説明や新しい設定は加えない。

**Sol の作業と合格条件。** 1回の履歴収集で全体件数・表示順・一致項目を決め、キャッシュ確認、レイアウト、UIA に同じ結果を使う。現在のピン留め・欠落ファイルの扱いと検索前の件数を基準にした列幅を維持する。初回空、1件一致、0件、Esc による復帰を2種類の表示で確認し、別窓の絞り込みや選択を動かさない。2B はこの見た目の変更を待たずに進められる。[Home の絞り込みとフォーカス](../../tests/ad-hoc-e88-home-focus-hover.ts) · [2窓のレイアウト](../../tests/home-two-windows.ts) · [ヒント表示](../../tests/home-tip-double-click.ts)

## 3. フォークの構成と保守

### 3A　低・再現　About の licenses 行が local build になる

**現象と根本。** Debug 版の About を開くと `source | GitHub repository` に続いて `licenses | local build` が表示された。SolokPDF 用の表では source が添字2、licenses が3。共通の `AboutCtrl::Sync` はフッター末尾から逆算した「source」の添字3に上流用のビルド情報と URL を書き込む。配布物のライセンス同梱とは別の案内ミスである。[表定義と同期](../../src/HomePage.cpp) · [上流用リンクの生成](../../src/shared/HomePageCommon.cpp) · [製品の仕様](features.md#portable-identity)

**Sol の作業と合格条件。** 製品用の静的リンクをそのまま使い、ビルド情報が必要な行は上流側の定義で明示する。フッターの位置からリンクの意味を推定しない。About を初回表示・再表示し、source はフォーク、licenses は定義済みの AUTHORS、フッターは上流サイト・マニュアルを指すこと。ラベルとリンク先を同時に読み、外部ブラウザーを起動せずに検証する。

## 着手順と完了の判定

1. **1A → 1B** の順に進める。失敗時の元データ保護と上書きの意思確認を別々に検証する。
2. **2A → 2B** を進める。利用者が検索・選択している対象を窓や文書の切替後も識別できることを重視する。
3. **3A → 2C** を進める。2C は使いやすさについての提案。現行仕様と照合し、採用した結果または現状を選んだ理由を記録する。

開始時に現行 HEAD と対象関数を照合する。各項目には「修正済み・現状維持・未検証」の判定、観測した出力、対象試験、コミットを残す。保留には再開条件を書く。各変更は独立して検証し、終了結果を [history.md](history.md) に移して [backlog.md](backlog.md) を更新する。

ローカルでは変更した C/C++ の整形後に Debug をビルドし、対象テストだけを非表示デスクトップで実行する。例えば 1A の部分失敗試験は内部で両 PDF エンジンを切り替える。寿命を変える 2B は同じ操作を ASan で追加確認する。[リポジトリの作業規約](../../agents.md) · [検証手順](testing.md)
