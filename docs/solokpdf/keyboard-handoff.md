## 目的

Win32 版の入力処理について、フォーカス・IME・モード・ショートカットの優先順位と、回数・接頭キーの状態管理を共通化できるか検討する。入力欄への文字入力とアプリのコマンド実行は区別する。

## 調査結果

- `src/VimKeys.cpp` の回数指定と Vim キー処理、および `src/SumatraPDF.cpp` のアクセラレーター選択は入力条件を別々に判定する。
- `src/shared/Accelerators.cpp` と `src/VimKeys.cpp` の双方に、ユーザー定義キーの優先順位に関わる判断がある。回数・接頭キーの消費や破棄も複数箇所に分散する。
- Sol の独立レビューは、入力コンテキスト、優先順位、状態管理を共通化する価値があると判断した。Edit・ComboBox・IME・目次・ダイアログそれぞれのネイティブな操作は維持する必要がある。
- フォーカスのないウィンドウにテストがメッセージを直接送ると、`3` は回数として認識されず `J` は処理される。通常のキーボード入力と区別する。
- 今回、Vim の `n`・`f` の後に未使用の回数が残る問題と、IME 変換中の上下キーでコマンド履歴が呼び出される問題を修正した。`3n` は検索を3回実行する機能ではない。

## 当時の次の作業（2026-11-04）

1. PDF 画面、検索欄、目次、ダイアログごとに、通常・Vim・ユーザー定義キー、回数指定、IME の期待動作を整理する。
2. 実メッセージ経路を通る代表的な回帰テストを補い、特に入力欄や目次の既存動作を固定する。
3. 入力コンテキストとルーターの設計案を比較し、優先順位と回数・接頭キーの状態管理を段階的に集約する。機能を一度に書き換えない。
4. AltGr、デッドキー、実際の日本語 IME、フォーカス移動、キーリピートを検証する。現在の IME テストは模擬メッセージであり、実 IME は未検証。
