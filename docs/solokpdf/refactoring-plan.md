# SolokPDF の設計とコードの見直し計画

最初の基準は `9083edafe`。Win32 版を対象とする。
E21 は `647da5a12` まで実装済み。E19 も実装・対象検証済み。
[現行設計](architecture.md) と [作業状態](backlog.md#design-review) を併せて参照する。

目的は、描画・色処理・読み取り・編集の責務と状態を明確にし、同じ判断の重複と暗黙の前提を減らすこと。
ファイル数や行数は完了条件にしない。描画品質・色の仕様変更は、動作を保つリファクタリングと分ける。

## 基準時点の評価

| 確認できた構造                                                                                   | 見直す理由                                                                       | 作業     |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- | -------- |
| `DarkModeProfile` と `RecolorPageColor` は共通化済み                                             | 色変換の計算は維持し、適用方針を整理する                                         | E21      |
| `RenderViewPage` はエンジン種別とモードから再着色の要否を判断する                                | 描画結果の色処理状態が暗黙で、二重変換や変換漏れを防ぐ契約が弱い                 | E19・E21 |
| PDF の smart は描画時の色変換後に補正し、legacy と Home の保存済みサムネイルは補正後に再着色する | 経路ごとの処理順を明示する必要がある                                             | E21      |
| 実効色の生成、タイルの世代、テーマ変換キャッシュ、サムネイルの hash は別々に管理される           | 出力に影響する入力と無効化条件の対応を追いにくい                                 | E22      |
| `DrawPage` の状態値・`useMupdf`、呼び出し側の `fallbackDrawn` が結果を表す                       | 成否、経路、中止、alpha の扱いが複数の変数にまたがる                             | E19      |
| `Try*` の `bool` は API ごとに意味が異なる                                                       | 空・未取得・別経路への委譲と、待機・編集エンジン生成の条件を明確にする必要がある | E18      |
| 元データ、編集中の文書、ページ情報、描画プローブは異なる寿命を持つ                               | 保存・再読み込み・破棄・ロックの整合性を操作ごとに確認する必要がある             | E20      |

これらはコード確認で得た設計上の論点であり、再現済みの不具合ではない。
文書全体のフォールバック、ページ単位の描画代替、遅延編集は別の判断として維持する。

## 基準と維持条件

変更する経路について、エンジン、描画対象、色モード、編集状態、透明度、補正の組合せを記録する。
通常表示、F12 ページサムネイル、Home の保存済みサムネイル、印刷・画像出力を区別する。
全組合せを実行するのではなく、異なる分岐と状態遷移を代表するケースを選ぶ。

- `off`・`smart`・`legacy` とセッション中の色反転を別の入力として扱う。
- 本文・画像・リンク・注釈・フォーム、パターン・グラデーション・マスクの既存の色を保つ。
- フォント選択、AA、解像度、タイル座標、印刷用フラグを変えない。
- 色変換、グレースケール、明度・コントラスト補正、alpha 処理、注釈合成の現在の順序を記録して保つ。
  経路間で順序が違っても、整理と同時に統一しない。変更が必要なら、期待出力を定義して別差分にする。
- PDFium と MuPDF で注釈を二重描画せず、墨消し適用済みページは編集内容を使う。
- 中止・失敗・古い世代の描画結果を公開しない。印刷・画像出力へ表示用テーマを意図せず適用しない。

比較は同じエンジン・経路・設定で変更前後を揃える。決定的な画素出力は一致を確認し、
エンジン間比較は既存テストの許容差を使う。速度・メモリは変更した経路だけ比較し、改善を前提にしない。

## E21 色方針と処理順を明確にする

最初の差分 `8bf864e18` で `GetPageColorPass` に通常描画と Home の中立画像の段階選択を集約した。
Debug・Release ビルドと対象検証・画素比較は [実施記録](history.md#e21-color-stage-policy-2026-11-10) を参照する。
`CapturePageColors` と `PageColorInput` に実効色の取得を集約し、
分類別のプロファイル生成へ渡す。描画結果の実施状態は E19 に残す。
E21 の段階選択と入力化の実装・対象検証は完了。E19 の結果契約に接続した。
結果と検証範囲は [実効色入力の記録](history.md#e21-effective-color-inputs-2026-11-10) を参照する。

対象は `PdfDarkModeProfile.cpp`、`PdfDarkModeColor.cpp`、`Theme.cpp`、`RenderViewPage`、
`FileThumbnailsCommon.cpp` と各エンジンの色処理入口。

1. 設定・プレビュー・色反転から実効色を決める処理と、描画対象・能力から変換方法を選ぶ処理を区別する。
   既存の `DarkModeProfile`・`ViewPageOptions` を活かし、必要な入力を描画ごとの値として確定する。
2. 色変換の担当段階、画像を保持する方式、補正順、透明度の要件を各経路に対応付ける。
   エンジン種別の判定は方針を決める境界に寄せ、後続処理が同じ判断を繰り返さない構造にする。
3. PDF 内部の変換、MuPDF 描画デバイスでの変換、ビットマップ再着色は、各経路の実装として残す。
   全経路を画素の後処理に置き換えない。Home の画像矩形による近似も、通常表示との違いとして明示する。
4. モードから導ける状態を新たなフラグとして重複保持しない。設定取得やプレビュー状態を低層の画素処理へ持ち込まない。

完了条件は、各経路について「何を、いつ、どこで色変換するか」を一意に説明でき、
現在の処理順と出力を維持できること。RGB 変換・補間・リンク色判定の計算変更は含めない。

## E19 描画実行と結果の契約を整理する

対象は `PrepareRenderRoute`、`DrawPage`、`RenderPage`、`RenderViewPage`、MuPDF 代替・注釈描画。

`PageDrawResult` に完了・代替要求・中止・失敗と色状態を分離した。
成功時の `RenderPageColor` と `Pixmap` の alpha 情報を呼び出し側へ渡し、
エンジン種別・`fallbackDrawn` からの推定を除いた。注釈合成失敗も結果を破棄する。
実装・対象検証は [E19 の記録](history.md#e19-render-results-2026-11-10) を参照する。
以下は元の完了条件として残す。

1. 経路判定と実行結果を区別する。既存の `PdfRenderRoute` は経路判定として使い、
   PDFium 固有の進行状態と `bool& useMupdf` は、完了・代替が必要・中止・失敗を表す結果へ整理する。
2. 色変換の担当と実施状態を E21 の方針・描画結果で確認できるようにする。
   呼び出し側がエンジン種別だけから変換済みと推定する構造を解消する。
   結果情報はまず描画経路内で扱い、全エンジンの戻り値や `Pixmap` を一括変更する必要性は別に判断する。
3. BGRA/BGR、alpha の有無、乗算済みか、背景へ合成済みかを入出力契約として揃える。
   `fallbackDrawn` から alpha 変換の要否を推定する箇所を見直し、二重乗算・二重合成を防ぐ。
4. 本文・注釈の描画元をタイル内で確定する。失敗・中止の解放と MuPDF 代替の実行箇所を追いやすくする。
   キャンセル確認点と非ロック部分の並列性は保つ。

完了条件は、成功結果の色・alpha・所有権が明確で、失敗・中止で画素バッファを返さず、
変換・合成・解放が各分岐で過不足なく行われること。描画品質を変えるアルゴリズム変更は分ける。

### 維持した分岐と失敗時の契約

`DrawPage`・`DrawMupdf`・`RenderPage` の契約。失敗を一律に MuPDF 再試行へ変えない。

| 条件                                                         | 現在の扱い                                         |
| ------------------------------------------------------------ | -------------------------------------------------- |
| 描画経路が MuPDF、テーマ変換失敗、一時文書・フォーム生成失敗 | 中止されていなければ MuPDF で描画する              |
| ページ読み込み失敗                                           | テーマ用文書なら MuPDF、それ以外は失敗             |
| ビットマップ生成失敗・PDFium 描画失敗                        | MuPDF へ再試行せず失敗                             |
| 注釈合成失敗                                                 | 本文の画素も破棄して失敗する                       |
| 中止                                                         | 結果を破棄する。MuPDF 代替も開始しない             |
| PDFium で透明な背景へ描画成功                                | 呼び出し側で alpha を乗算する                      |
| MuPDF 代替で透明な背景へ描画成功                             | 乗算済みとして扱い、再乗算しない                   |
| 墨消し適用済みページ                                         | タイル生成前に編集エンジンの `RenderPage` へ委ねる |

## E22 キャッシュの依存と無効化を揃える

対象は `UpdateDocumentColors`、`RenderCache`、PDFium のテーマ変換キャッシュ、ページ・Home サムネイル。

1. 各キャッシュについて、保存する値、出力へ影響する入力、有効期間を一覧にする。
   テーマ変換結果、最終画素、テーマ非依存のページ描画経路、画像矩形、Home の中立 PNG を区別する。
2. 色・モード・画像保持・補正などの依存を E21 の確定値から求める。
   プロファイル生成と無効化側で実効色を独立に組み立てる重複を減らす。
   世代番号と hash は用途が違うため、一律に置き換えない。
3. 色変更中の要求をどう破棄するか、テーマ復帰で何を再利用するかを確認する。
   編集・墨消し・再読み込みの無効化も、文書状態の変更と対応付ける。
4. キーの変更で不要な再変換・再描画が増えていないか確認する。
   容量・LRU・単一の大きなエントリーの扱いは、必要性を確認せず変更しない。

完了条件は、出力に影響する入力が再利用条件に反映され、古い要求が公開されず、
テーマ非依存の情報まで不要に破棄しないこと。タイル世代と各キャッシュの役割を説明できる状態にする。

## E18 読み取りと編集要求の契約を明確にする

対象は `EngineBase.{h,cpp}`、`EngineCreate.cpp`、`EnginePdfium.cpp` と呼び出し側。

1. テキスト・リンク・hover・フォーム・注釈ごとに、待機、編集エンジン生成、結果の完全性、再試行の条件を決める。
2. 機能の対応可否、文書の権限、編集エンジンの生成状態を区別する。
   `HasAnnotationEditor` を「生成済み」や「編集可能」の代用にしない。
3. 必要な経路では取得済み・保留・別経路が必要という結果を区別する。
   `EditorLoad`、`PageText::partial` と既存の呼び出し側契約を活かし、公開 API の変更範囲を決める。

完了条件は、hover・paint が新たに編集エンジンを生成・待機せず、検索が不完全な文字列を
完全な結果としてキャッシュしないこと。権限・生成失敗・未取得時の動作を保つ。
非 PDF エンジンや共有コードへの影響を確認し、全 `Try*` の形式だけを揃える変更は行わない。

## E20 文書状態と寿命の整合性を点検する

1. 元データ、PDFium 文書、遅延編集、描画プローブ、ページ情報、テーマ変換結果の
   所有者・借用先・有効期間・必要なロックを対応付ける。
2. 開く、編集生成失敗、編集、墨消し適用・Undo、保存、再読み込み、複製、閉じるの状態遷移を確認する。
   元データのコピーと編集内容の保存は別の操作として保つ。
3. `gPdfiumLock`・`themeLock`・`editorLock`・MuPDF 側のロックが実際に入れ子になる経路を確認する。
   パスワード UI、外部コールバック、描画中止、サムネイルの破棄・ワーカー終了も対象にする。
4. 暗黙の借用、重複する状態、不要な組合せを見つけた箇所だけ変更する。
   参照カウントと終了順序を守り、管理用クラスの追加自体を目的にしない。

完了条件は、変更した状態の遷移・解放・ロック条件を説明でき、保存元の取り違えや破棄後の参照を防ぐこと。
点検で変更不要と判断した経路は理由を記録して終える。

## 対象検証

変更前後で下表から影響するテストを選ぶ。列挙した全テストを毎段階で実行するものではない。
既存テストを優先し、重要な分岐・遷移の不足だけを補う。

| 変更対象                           | 使う既存テスト                                                                                                                                       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 色モード・画像保持・補正順         | `ad-hoc-pdfium-theme`、`ad-hoc-pdfium-theme-switch`。明度・コントラスト・グレースケールとの組合せは既存検証の範囲を確認して補う                      |
| ページ描画代替・透明度             | `theme-transparent-fallback`、`theme-fallback-tiles`、`theme-fallback-geometry`、`ad-hoc-pdfium-tiles`                                               |
| 描画中止                           | `theme-render-cancel`。MuPDF のパターン経路は `SOLOKPDF_TEST_PATTERN_STROKES=1` でも確認する                                                         |
| 注釈合成失敗                       | `theme-annotation-failure`。合成失敗を注入し、本文だけを成功結果として返さないことを確認する                                                         |
| マスク・パターン・Type 3・フォーム | `theme-pattern-colors`、`theme-type3`、`theme-state-widget`、`theme-dynamic-widget`。変換失敗時のまとめ検証は `theme-pdfium-fallback`                |
| キャッシュ・サムネイル             | `theme-pdfium-cache`、`ad-hoc-pdfium-theme-switch`、`ad-hoc-pdfium-thumb-theme`。中立 PNG・補正値・古い要求の破棄は変更箇所ごとに既存検証を確認する  |
| 読み取り・編集                     | `ad-hoc-pdfium-try-reads`、`ad-hoc-pdfium-hover`、`ad-hoc-pdfium-form-hover`、`ad-hoc-pdfium-text`。権限・フォームを変える場合は対応テストを追加する |
| 文書状態・所有権                   | `ad-hoc-pdfium-redaction-undo`、`ad-hoc-pdfium-saveas`、`ad-hoc-pdfium-memory`、完全版 `ad-hoc-pdfium`。反復寿命を変える場合は `ad-hoc-pdfium-leak`  |

`ad-hoc-pdfium-thumb-theme` の既存のグレースケール確認も再利用する。
共有の色方針を変える場合は、影響する非 PDF 経路を選び、EPUB は `epub-theme-restyle` で確認する。
`theme-pdfium-cache` はページ再訪・ズーム時の変換再利用を確認するもので、無効化全体を網羅しない。
`ad-hoc-pdfium --fallback-only` は DLL 不在時の文書フォールバックであり、ページ描画代替の検証にはならない。
色の数値計算や base の画素処理を変える場合は、既存の単体テストを含む `bun cmd/run-unit-tests.ts -dbg` も実行する。

ローカル GUI 検証は [testing.md](testing.md#local-windows-runs) の非表示デスクトップで行う。
C++ 整形後に Debug をビルドし、ビルド完了後の固定した実行ファイルで対象検証を行う。
各作業の最終段階で Release もビルドする。寿命・所有権を変えた経路は ASan でも確認する。
プリビルド PDFium 内部は ASan の対象外。全スイートは明示的な依頼がある場合だけ実行する。

不具合を見つけた場合は、失敗するテストを先に確認し、修正をリファクタリングと分ける。
各作業で基準リビジョン、構成、入力、対象テスト、画素比較、ログ、未確認範囲を記録する。

## 範囲と完了判断

UI はエンジンの操作 API を使い、PDFium API・MuPDF 内部への新しい直接アクセスを追加しない。
既存の `EngineCreate`・`EngineBase`・描画 API を改善できるなら優先する。共有コードは非 PDF と ng の互換性も確認する。
入力先・キー状態・仮想ツリー・ランタイムの完了済み整理は維持し、追加変更は具体的な問題を特定した場合に限る。
ng の機能開発、配布、F1/F3 の実機確認は今回の対象に追加しない。

完了は「重複する判断が減った」「状態・副作用・処理順を契約から追える」「対象の既存出力を保った」で判断する。
ファイル分割、抽象クラス追加、性能向上は必須条件にしない。
実装結果は `history.md`、現行設計は `architecture.md` に反映する。コミットは明示的な指示後に行う。
