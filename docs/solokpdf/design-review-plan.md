2026-11-21。基準は `solokpdf-dev` の `c75f0b75c`。Win32 製品の利用者操作から、共通層・両 PDF エンジン・配布・検証までを追った静的レビュー。以下の 32 件はこの調査で根拠を特定できた指摘と提案である。全ソースの監査や実機での不具合再現は行っていない。

### 判断と引き継ぎ

- **優先度**　高＝別文書や予期しない内容の出力、部分失敗の見落とし、作業対象外への副作用。中＝利用者操作の一貫性、不要な仕事、変更時に崩れやすい契約。低＝変更機会や測定結果に応じて採用する提案。
- **種類**　「差」はコードで分岐または出力差を確認。「調査」は影響・発生条件を再現して決定。「提案」は現行仕様でも成立する保守改善。観察した構造と実害を分ける。差についても実機再現の成否を記録する。
- **出力仕様の作業仮定**　開いているタブから作る派生文書は、操作開始時に指定したタブの確定済み編集を含む。ツールが意図的にディスク上のファイルを扱う場合は入力を画面で識別できること。ファイルを選び足す Merge、元バイトのコピー、変換で保持できない署名等を一律に同じ意味にしない。既存の明示仕様と衝突した行は二案と影響を記録し、独立項目を先行する。
- **記録**　開始時に対象 ID、現在の HEAD、対象の入口と既存テストを記入。終了時は `ID / 採用・現状維持・保留 / 根拠 / 実行した検証・結果 / commit / 次のID` を backlog からたどれるようにする。保留には再開条件を一つ書く。再開時は現行コードで解消済みなら変更せず確認結果を残す。
- **実装単位**　挙動を変える項目、境界の整理、計測は別々に検証できる単位にする。バグは該当テストの失敗を観察してから修正し、同じテストの成功を確認する。計測は同じ Debug バイナリ条件、文書、操作、キャッシュ状態で変更前後を反復し、件数・分布・ばらつきを併記する。単発の時間差で採用しない。

**R11 中・差 — `Clone()` の戻り値から隔離の有無を判断できない。** 通常は再オープンするが、適用済み墨消しがあると現行エンジンを AddRef して返す。印刷・サムネイルでは正しい内容を届けるための意図的な共有である。呼び出し元が必要とするのが寿命、独立した設定、ある時点の内容のどれかを列挙し、独立性を実際に必要とする箇所だけ契約を分ける。出力中の Undo／タブを閉じる操作で古い本文の再出現、寿命違反、dirty の変化がないか確認。既存仕様を確認できれば明文化で完了。[Clone](../../src/solokpdf/EnginePdfium.cpp) · [共有する理由と参照保持](../../src/shared/EngineMupdf.cpp)

**R12 中・差 — `Try` を呼んでも UI スレッド上の仕事量が一定しない。** 基底の `TryExtractPageText`／`TryGetElements` は同期 API に委譲する。PDF エンジンでもロックをすぐ取れてからの冷えたページ解析には時間がかかる。ホバー・クリック・先読みの各呼び出しを調べ、待ってよい操作と未確定を返せる操作を区別する。操作中の UI を止める具体例のみ修正し、既存の Pending／部分テキスト／完全取得の意味を保存する。[基底実装](../../src/shared/EngineBase.cpp) · [読取契約](architecture.md#読み取り-api-の契約) · [既存テスト](../../tests/ad-hoc-pdfium-try-reads.ts)

**R13 低・調査 — ページラベル付き文書では初回表示前に全ページを調べる。** `LoadPageLabels` は先頭でラベルの有無を検査し、ある場合だけ全ページ分の文字列と論理ページ数を作る。ラベルなし、ラベルあり、重複・ローマ数字を含む合成多ページ PDF で `labels` の時間と保持量を比較する。負担が有意なら逆引きや論理ページ数を最初に要求した時点へ遅延できるか検討。初回表示・ジャンプ・重複ラベルの従来結果の三つが合う場合だけ採用。[LoadPageLabels](../../src/solokpdf/EnginePdfium.cpp)

**R14 低・調査 — ファイル保持方式と機能検出の打ち切り条件が同じサイズ定数に結び付く。** 32 MiB の前後でメモリ保持、カタログ・注釈の事前走査、補助パーサーを使う条件が変わる。内容が等しく長さだけが境界直下・直上の資料を用い、open、パレット、初回表示で追加解析数を記録する。既存の安全側フォールバックを維持し、二つの判断を独立に変更すべき証拠がある場合だけ分離する。[入力方式とキー走査](../../src/solokpdf/EnginePdfium.cpp) · [カタログ検証](../../tests/ad-hoc-pdfium-catalog-layout.ts)

## 5. 描画・検索・応答性

**R21 中・調査 — 編集を繰り返すタブで、古い検索文字列が文書の寿命まで残る。** `PageTextCache` は呼び出し元が生ポインターを借用するため、失効後に再利用できない文字列・座標を退避する。通常の開閉テストだけでは長時間開く編集タブの負担が分からない。フォームの値を変え、検索で再抽出するサイクルと、同じ値の対照群で退避件数・バイト数を測る。コストが確認できたら借用者を特定し、最後の借用終了後にだけ解放する。Undo、選択中の再描画、検索結果更新を ASan でも確認。[テキストキャッシュ](../../src/shared/EngineBase.cpp) · [検索世代](../../src/shared/TextSearch.cpp) · [フォームと検索](../../tests/form-text-cache.ts)

**R22 中・調査 — 別タブの重い処理が、現在タブの文書操作を待たせる。** PDFium のプロセス共通ロックを描画と文字抽出が共有する。既にロック ID ごとの中止があるが、初回解析や一部 API の実行中には中止点がない。A で冷えたページの描画・文字先読み、B でクリックとホバーを分け、待機、実処理、中止からの回復を計測する。待機が再現する生産側だけ、仕事の延期や優先順位を検討。PDFium の直列呼び出しと、完了を必要とするクリックの結果を保存する。[AbortForAction](../../src/shared/RenderCache.cpp) · [競合ごとの既知の回復](limitations.md#engine-contention-e133) · [負荷を固定するテスト](../../tests/ad-hoc-e128-busy-render.ts)

**R23 中・提案 — 文書表示と Home の再着色に必要な入力を二重に追う必要がある。** 色処理段階の共通判定は既にある。一方、変換済み画素、画像保持矩形、明度・コントラストの依存は、描画ルートと Home の表示用コピーで別々に扱う。色オプションを一つ追加した場合に更新するキーと invalidation を現在の設計表に照合。漏れを発見した時だけ共通の入力から導出する。本文・F12・Home で明暗切替後の文字色と写真を比較し、Home の中立 PNG とリフロー済み画像の扱いを維持する。[色処理段階](../../src/shared/PdfDarkModeProfile.cpp) · [Home の表示キー](../../src/shared/FileThumbnailsCommon.cpp) · [サムネイル色テスト](../../tests/ad-hoc-pdfium-thumb-theme.ts)

**R24 低・調査 — Home の PNG と色の補助データは別々に更新される。** PNG のエンコード成功後に以前の補助ファイルを消し、PNG 置換成功後に新しい補助データを書く。途中失敗時は有効な旧 PNG が残っても写真保持矩形を失う経路がある。専用キャッシュで PNG 置換失敗と補助書込失敗を分け、次回起動の見え方を確認する。影響が見えれば旧ペア保持または再生成を選ぶ。旧形式・欠落ファイルのフォールバックは維持する。[PNG の公開順序](../../src/FileThumbnails.cpp) · [補助データの読取と公開](../../src/shared/FileThumbnailsCommon.cpp)

**R25 中・調査 — 複数ページ画像出力は操作スレッド上で完了まで走る。** 待機カーソルを出して同期変換を呼ぶため、大きい出力ほどウィンドウの操作性に影響し得る。R04 の部分成功と R05 の対象検証後、通常の複数ページで処理時間・メッセージ応答を測る。必要なら既存ワーカーの所有・中止パターンを利用し、進捗・確定済み出力を表示する。文書を閉じる、回転を変える、中止する場合も開始時の対象・回転を守り、完了時に失効した窓へ通知しない。[画像変換ダイアログ](../../src/PdfTools.cpp) · [ページ単位の変換](../../src/shared/PdfToolsCommon.cpp)

## 6. フォーク・ビルド・配布

**R26 低・提案 — バックエンド選択が製品名・更新方針・メニュー構成を兼ねる。** `--with-pdfium` の製品では `SOLOKPDF_PDFIUM` がこれらすべてを切り替える。実行時に MuPDF を選んでも SolokPDF のままである。次の該当変更で製品ポリシーとリンク機能に別名を与え、同じ配布構成から設定する。製品名・設定ファイル・更新無効・メニューがどちらの実行時エンジンでも同じであることを確認。組み合わせビルドを増やす必要はない。[ラッパー](../../cmd/solok-build.ts) · [製品名](../../src/shared/Version.h) · [更新方針](../../src/shared/UpdateCheck.h) · [共存テスト](../../tests/ad-hoc-solok-coexist.ts)

**R27 低・提案 — 展開済みフォルダーと ZIP の内容保証が異なる。** 配布フォルダーは上書きコピー、ZIP は今回のマニフェストから作る。以前の構成にだけあった DLL／告知ファイルや、今回生成されなかった PDB は再利用フォルダーに残り得る。専用の作業ディレクトリで旧版→新版の連続ステージを再現する。対応する場合は前回マニフェストで管理したファイルのみ整理し、利用者の設定・メモ・追加ファイルを保護する。ZIP、展開版、シンボルの意図した差を検証。[配布処理](../../cmd/helper/solok-portable.ts) · [ZIP 検証](../../tests/ad-hoc-solok-portable.ts)

**R28 低・提案 — quick と通常 Debug では検証できる資材が異なる。** quick は直接 MSBuild、通常は共通ビルドの文書生成・ステージングを通る。quick 成功だけでは、埋め込みマニュアルや配布フォルダーへの変更を確認できない。quick の速さは残し、手順の対象を「アプリのみ」「埋め込み資材」「ZIP」に分ける。既存手順で判別できれば追記のみ、実際に古い資材を検証した例があればその入口だけ修正する。[二つのビルド経路](../../cmd/solok-build.ts) · [文書生成](../../cmd/build.ts) · [既存の ZIP 手順](testing.md#portable-zip)

## 検証・終了条件

リポジトリルートで実行する。以下は R01 の回帰テストを両エンジンで実行する例。テスト自身がエンジンを切り替える場合は二重に回さない。

```powershell
. ./tools/solokpdf/env.ps1
bun cmd/solok-build.ts -quick
$env:SOLOKPDF_ENGINE = 'pdfium'
bun tools/solokpdf/run-hidden.ts -- bun tests/pdf-tools-encrypted.ts --no-build
$env:SOLOKPDF_ENGINE = 'mupdf'
bun tools/solokpdf/run-hidden.ts -- bun tests/pdf-tools-encrypted.ts --no-build
Remove-Item Env:SOLOKPDF_ENGINE
```

- ローカルでアプリを起動するテストは [hidden desktop 手順](testing.md#local-windows-runs) に従う。手動起動時は `-for-testing`。環境変数の例は専用シェルで実行する。対象の寿命・解放を変える場合は [ASan 手順](testing.md#asan-builds) の該当ケースを追加。ローカル Release と無関係な全件テストは実行しない。
- [agents.md](../../agents.md) に従い、変更した C/C++ をビルド前に clang-format、TS はリポジトリの formatter、Markdown は Prettier で整形する。検証済みの作業単位を現在の upstream に通常 push する。共有ファイルを触る時も対象製品は Win32。凍結済み ng、サイト全体、配布方針の変更は [対象外の一覧](backlog.md#not-planned) に従う。
- 受け入れは各 ID の観測結果で決める。出力ならファイルを開き直した結果、対象固定なら別タブに副作用がなかった結果、性能なら比較値が必要。専用環境がなければ「未確認」と明記し、合格扱いにしない。仕様変更は features／limitations、責務変更は architecture、実行結果は history に反映する。
- 全 ID に判定・根拠・検証・残件が付いた時点で総括する。保留を完了に数えない。既存のプロジェクト方針どおり、解決済みの結果を履歴に移し、現役の計画と backlog へのリンクを整理する。
